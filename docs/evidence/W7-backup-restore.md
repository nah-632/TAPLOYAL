## 4. ⛔ حدّ الاستعادة على الخطة المجانية — بكلمات المنصة

محاولة استعادة **فعلية** إلى قاعدة جديدة (`into: "new"`، وهي غير مُدمِّرة):

```
restore status: failed
error: "Your free plan allows up to 2 application(s) and database(s) combined.
        Please upgrade to create more."
```
**السبب:** `limits.apps_and_databases = 2` و`usage = 2` (تطبيق واحد + قاعدة واحدة).

⇒ على هذه الخطة لا يوجد إلا مسار واحد لاستعادة حقيقية: **`into: "replace"`** — وهو **مُدمِّر على قاعدة الإنتاج الحيّة** (المنصة تأخذ نسخة أمان قبله). **لم أنفّذه**: يحتاج موافقتك الصريحة.

## 5. ما أُثبت وما لم يُثبت — بصراحة

| العبارة | الحالة |
|---|---|
| النسخة الاحتياطية تُؤخذ يوميًا وتُحفظ 14 يومًا | ✅ مُثبت |
| الأرشيف **صالح وكامل البنية** (جداول + دوال + فهارس + قيود) | ✅ مُثبت بـ`pg_restore -l` |
| الأرشيف **يحوي البيانات** (25 صفًا مقروءة) | ✅ مُثبت بـ`pg_restore -a` |
| **استعادة حيّة نُفِّذت بنجاح وطابقت المصدر** | ❌ **لم تُنفَّذ** — محجوبة بالخطة أو بمخاطرة `replace` |

**لا أدّعي** أن الاستعادة مُثبتة. أدّعي أن الأرشيف مُثبت الصلاحية والاكتمال، وأن العائق للاستعادة الحيّة مُشخَّص بنصّ المنصة.

## 6. نظافة الإنتاج

- ✅ أُسقطت `_rls_probe` · `_engine_probe` · `_onb_probe` — كانت مخلفات مجموعات الاختبارات التي تعمل عبر الـAPI، وظهرت **داخل** النسخة الاحتياطية.
- ⚠️ باقٍ: تاجران وهميان (`tenant-a`, `tenant-b`) مع بياناتهما في قاعدة الإنتاج من نفس المجموعات.
- ✅ أُعيد الوصول الخارجي إلى **مغلق** بعد الانتهاء، والإنتاج يعمل (`GET /` ⇒ 200).
