1. الدور والهدف (ROLE & OBJECTIVE)
==================================================

أنت فريق تقني متكامل يضم الأدوار التالية:

- Senior SaaS Product Architect.
- Senior Full-Stack Engineer.
- Database Architect.
- Apple Wallet / PassKit Integration Engineer.
- Google Wallet API Integration Engineer.
- UI/UX Designer.
- Security Engineer.
- DevOps Engineer.
- QA & Automation Engineer.

مهمتك هي تصميم وبناء منصة SaaS متكاملة ومتعددة التجار (Multi-Tenant Digital Loyalty Platform)، تتيح لأي مشروع تجاري إنشاء وإدارة برنامج ولاء رقمي خاص به، وإصدار بطاقات ولاء تحمل هويته البصرية، ليتمكن عملاؤه من إضافتها مباشرة إلى Apple Wallet أو Google Wallet دون الحاجة إلى تنزيل تطبيق مستقل.

المنصة تستهدف:

- المقاهي.
- المطاعم.
- صالونات التجميل.
- محلات التجزئة.
- المتاجر المتخصصة.
- المشاريع الصغيرة والمتوسطة.

النطاق الجغرافي المستهدف: دول الخليج العربي والوطن العربي، مع قابلية التوسع عالميًا.

النموذج الربحي:

1. Free: خطة مجانية بحدود استخدام محددة.
2. Basic: خطة اشتراك شهرية للمشاريع الصغيرة.
3. Professional: خطة اشتراك شهرية للمشاريع ذات الاحتياجات المتقدمة.

المبدأ الأساسي للمنتج:

اجعل إنشاء برنامج ولاء وإطلاقه عملية بسيطة لا تستغرق أكثر من دقائق معدودة.

يجب ألا يحتاج التاجر إلى معرفة تقنية أو خبرة في تصميم البطاقات أو التعامل مع شهادات Apple أو Google.

لا تبنِ مجرد واجهة عرض أو نموذج أولي بصري. ابنِ منتج SaaS حقيقيًا، ببنية قابلة للتوسع، وقاعدة بيانات فعلية، ومصادقة حقيقية، وصلاحيات محكمة، وتكاملات Wallet قابلة للاستخدام الفعلي.

اعتمد مبدأ:
Production-Ready Architecture, Incremental Delivery, Security by Design.

لا تدّعِ أن أي تكامل خارجي يعمل قبل تنفيذ اختباره الفعلي بنجاح.

2. المستخدمون والأدوار والصلاحيات
==================================================

أنشئ أربعة أدوار أساسية، مع عزل صارم للبيانات والصلاحيات.

A. التاجر (Merchant / Owner)

يمتلك حسابًا تجاريًا مستقلًا يستطيع من خلاله:

- إنشاء وإدارة بيانات نشاطه التجاري.
- رفع الشعار وتحديد الهوية البصرية.
- إنشاء برنامج ولاء.
- تصميم بطاقة الولاء.
- تحديد نظام النقاط أو الأختام.
- تحديد المكافآت وشروط استحقاقها.
- إنشاء موظفين وتحديد صلاحياتهم.
- إنشاء رموز QR للانضمام.
- مشاهدة العملاء والمعاملات.
- الاطلاع على الإحصائيات.
- إدارة الاشتراك والفواتير.
- تعديل بيانات برنامج الولاء.

يُسمح للتاجر بالوصول إلى بيانات مؤسسته فقط.

B. الموظف (Staff)

يمتلك حسابًا مرتبطًا بتاجر محدد.

يستطيع:

- تسجيل دخول آمن.
- فتح واجهة الموظف المبسطة.
- البحث عن عميل أو مسح رمز QR الخاص به.
- تسجيل زيارة أو إضافة نقاط وفق صلاحياته.
- استبدال المكافآت عند السماح بذلك.
- مشاهدة سجل المعاملة التي نفذها.

لا يستطيع:

- تغيير إعدادات البرنامج.
- تعديل الاشتراك.
- الوصول إلى إعدادات التاجر.
- إنشاء موظفين آخرين.
- الاطلاع على بيانات مالية أو إحصائيات غير مصرح بها.

أضف صلاحيات قابلة للتخصيص لكل موظف، مثل:

- earn_points.
- redeem_rewards.
- view_customers.
- reverse_transactions.

C. العميل النهائي (Customer)

لا تشترط إنشاء حساب تقليدي لاستخدام البطاقة.

يستطيع:

- الانضمام إلى برنامج الولاء عبر QR.
- إدخال رقم الهاتف أو البريد الإلكتروني حسب إعدادات التاجر.
- الحصول على بطاقة ولاء رقمية.
- إضافة البطاقة إلى Apple Wallet.
- إضافة البطاقة إلى Google Wallet.
- مشاهدة رصيد النقاط أو الأختام.
- مشاهدة المكافآت المتاحة.
- تلقي تحديثات البطاقة.
- استعراض معلومات برنامج الولاء.

أنشئ صفحة ويب خفيفة للعميل يمكن الوصول إليها من رابط البطاقة.

D. المشرف العام (Super Admin)

يمتلك صلاحيات الإدارة المركزية الكاملة.

يستطيع:

- مشاهدة جميع التجار.
- إنشاء وتعديل وتعليق حسابات التجار.
- مشاهدة الاشتراكات.
- إدارة الخطط والأسعار.
- متابعة الإيرادات والاشتراكات النشطة.
- مراقبة استهلاك الموارد.
- الاطلاع على سجلات النظام.
- إدارة إعدادات المنصة العامة.
- مراقبة عمليات إصدار وتحديث البطاقات.
- إدارة حالات فشل التكامل مع Apple وGoogle.
- إدارة الدعم الفني.
- مراجعة العمليات المشبوهة.

افصل صلاحيات Super Admin عن صلاحيات التاجر بصورة كاملة.

3. رحلات المستخدم (USER JOURNEYS)
==================================================

A. رحلة التاجر

1. يدخل التاجر إلى الصفحة الرئيسية.
2. يضغط على "ابدأ مجانًا".
3. ينشئ حسابًا بالبريد الإلكتروني وكلمة المرور.
4. يتحقق من البريد الإلكتروني.
5. يدخل إلى معالج الإعداد الأولي.
6. يحدد اسم النشاط التجاري ونوعه ودولة التشغيل.
7. يرفع الشعار.
8. يختار ألوان البطاقة.
9. يحدد نوع برنامج الولاء:
   - Stamp Based.
   - Points Based.
10. يحدد شروط الحصول على النقاط أو الأختام.
11. ينشئ المكافآت.
12. يشاهد معاينة حية للبطاقة.
13. يعتمد تصميم البطاقة.
14. ينشئ النظام بطاقة الولاء ويجهز تكاملات Wallet.
15. يحصل التاجر على رابط انضمام ورمز QR.
16. يضع رمز QR في متجره.
17. يبدأ العملاء بالانضمام.
18. يستخدم الموظفون واجهة تسجيل النقاط.
19. يتابع التاجر الأداء من لوحة التحكم.

B. رحلة الموظف

1. يستلم الموظف دعوة من التاجر.
2. ينشئ حسابه أو يقبل الدعوة.
3. يسجل الدخول.
4. يختار الفرع إذا كان التاجر يمتلك عدة فروع.
5. تظهر له واجهة تسجيل العمليات.
6. يمسح QR العميل أو يبحث عن رقم هاتفه.
7. يتحقق النظام من هوية العميل وانتمائه لبرنامج التاجر.
8. يسجل الموظف عملية إضافة نقاط أو ختم.
9. يحدّث النظام رصيد العميل.
10. يرسل تحديثًا للبطاقة الرقمية عند توفر التكامل.
11. يعرض النظام تأكيد العملية.

C. رحلة العميل

1. يمسح QR الموجود في المتجر.
2. تفتح صفحة الانضمام.
3. يشاهد اسم النشاط التجاري وشعاره وبرنامج الولاء.
4. يوافق على الشروط وسياسة الخصوصية.
5. يدخل البيانات المطلوبة.
6. يتحقق من رقم الهاتف عند اشتراط ذلك.
7. ينشئ النظام سجل العميل.
8. يصدر النظام بطاقة ولاء مرتبطة بالعميل.
9. تظهر خيارات:
   - Add to Apple Wallet.
   - Add to Google Wallet.
10. يضيف العميل البطاقة إلى المحفظة المناسبة.
11. يعود إلى صفحة نجاح الانضمام.
12. يستطيع الاطلاع على رصيده ومكافآته.

يجب توفير تجربة بديلة عبر المتصفح عندما لا يكون الجهاز متوافقًا مع إحدى المحافظ.

D. رحلة المشرف العام

1. يسجل الدخول عبر بوابة الإدارة المنفصلة.
2. يخضع للتحقق متعدد العوامل.
3. يشاهد لوحة مؤشرات المنصة.
4. يتابع التجار والاشتراكات.
5. يراجع حالات النظام.
6. يتابع عمليات إصدار البطاقات.
7. يتعامل مع البلاغات والمشكلات.
8. يراجع سجلات التدقيق.
9. يدير الخطط والحدود التشغيلية.

8. APPLE WALLET — PASSKIT TECHNICAL FLOW
==================================================

هذا القسم من أهم أجزاء المشروع.

نفّذ Apple Wallet بطريقة صحيحة وفق متطلبات Apple الرسمية.

A. Apple Developer Configuration

أنشئ إعدادًا مركزيًا للمنصة يعتمد على:

- Apple Developer Account.
- Pass Type ID.
- Pass Type ID Certificate.
- Certificate Private Key.
- Apple WWDR Intermediate Certificate.
- APNs Integration.

B. استراتيجية الشهادة الموحدة Multi-Tenant

لا تطلب من كل تاجر استخراج شهادة Apple Developer خاصة به.

اعتمد نموذجًا مركزيًا:

1. تمتلك المنصة حساب Apple Developer الخاص بها.
2. تنشئ Pass Type ID واحدًا أو مجموعة Pass Type IDs مخصصة للمنصة حسب الحاجة التشغيلية.
3. تحصل على الشهادات المطلوبة.
4. تحفظ المفاتيح الخاصة بصورة آمنة.
5. تستخدم Pass Type ID مركزيًا لإصدار بطاقات جميع التجار.
6. تميز بطاقات التجار باستخدام serialNumber فريد لكل بطاقة.
7. تضع هوية التاجر البصرية وبيانات برنامج الولاء داخل البطاقة.
8. تربط كل بطاقة بسجلها داخل قاعدة البيانات.

يجب أن يكون واضحًا أن Pass Type ID المركزي يمثل الجهة المصدرة للبطاقات، وليس التاجر الفردي.

لا تنشئ Pass Type ID مستقلًا لكل تاجر إلا إذا كان هناك سبب تقني أو تجاري يستدعي ذلك.

C. Pass Generation Flow

عند طلب إصدار بطاقة:

1. تحقق من العميل والتاجر والبرنامج.
2. أنشئ سجل Pass داخل قاعدة البيانات.
3. أنشئ serialNumber فريدًا.
4. جهّز ملف pass.json.
5. أضف الشعار والصور المطلوبة.
6. أضف بيانات البطاقة.
7. أضف الرصيد الحالي.
8. أضف بيانات المكافآت أو معلومات البرنامج المناسبة.
9. أضف webServiceURL.
10. أضف authenticationToken فريدًا للبطاقة.
11. أنشئ ملف ZIP وفق مواصفات PassKit.
12. وقّع الحزمة باستخدام شهادة Pass Type ID والمفتاح الخاص المرتبط بها.
13. أرفق شهادة WWDR المطلوبة.
14. أنشئ ملف .pkpass صالحًا.
15. أرسله إلى العميل عبر HTTPS.
16. وفر رابطًا آمنًا لإعادة تنزيل البطاقة.

D. Pass Fields

ادعم الحقول المناسبة:

- organizationName
- description
- logoText
- foregroundColor
- backgroundColor
- labelColor
- serialNumber
- passTypeIdentifier
- teamIdentifier
- authenticationToken
- webServiceURL

استخدم نوع البطاقة المناسب لبرنامج الولاء، مثل storeCard، وفق بنية PassKit.

E. Pass Updates

عندما يسجل الموظف نقاطًا أو أختامًا:

1. تحقق من صلاحية المعاملة.
2. حدّث رصيد العميل داخل Database Transaction.
3. أنشئ سجل Transaction.
4. حدّث بيانات البطاقة.
5. أضف مهمة تحديث إلى Background Queue.
6. حدد الأجهزة المسجلة لهذه البطاقة.
7. أرسل إشعار APNs المناسب إلى الأجهزة.
8. عندما يطلب جهاز العميل تحديث البطاقة، قدم أحدث نسخة من بيانات Pass.
9. أعد توقيع ملف البطاقة.
10. أرسل بيانات التحديث عبر Web Service الخاص بـ PassKit.

لا تخلط بين APNs وإرسال محتوى البطاقة.

APNs يستخدم لتنبيه الأجهزة بوجود تحديث، بينما يجلب الجهاز نسخة البطاقة المحدثة من Web Service الخاص بالمنصة.

F. PassKit Web Service

نفّذ المسارات المطلوبة وفق بروتوكول Apple PassKit Web Service، بما في ذلك:

- تسجيل الجهاز.
- إلغاء تسجيل الجهاز.
- الاستعلام عن البطاقات المحدثة.
- تنزيل البطاقة المحدثة.

تحقق من جميع المسارات والترويسات ومتطلبات المصادقة وفق وثائق Apple الرسمية.

G. Certificate Management

- لا تضع الشهادات داخل مستودع Git.
- لا تخزن المفاتيح الخاصة كنصوص مكشوفة.
- استخدم Secret Manager أو KMS مناسبًا.
- خطط لتجديد الشهادات قبل انتهاء صلاحيتها.
- راقب انتهاء الصلاحية.
- وفر آلية لتدوير المفاتيح.
- لا تسمح بوصول التجار إلى الشهادة أو المفتاح الخاص.

H. External Dependencies

صرّح بوضوح أن تشغيل Apple Wallet الفعلي يحتاج:

- Apple Developer Account.
- Pass Type ID.
- شهادة صالحة.
- مفتاح التوقيع الخاص.
- APNs Configuration.
- HTTPS Endpoint.
- بيئة اختبار متوافقة مع Apple Wallet.

لا تدّعِ نجاح إصدار البطاقات دون اختبار ملف .pkpass على جهاز فعلي.

- التحقق من الصلاحيات في الخادم.
- انتهاء صلاحية الجلسات عند الحاجة.

3. Data Protection

- HTTPS لجميع الاتصالات.
- تشفير البيانات الحساسة أثناء النقل والتخزين.
- حماية بيانات العملاء.
- عدم تخزين بيانات غير ضرورية.
- تقليل الوصول إلى بيانات العملاء.
- عدم تسجيل كلمات المرور أو الرموز السرية في Logs.

4. API Security

- Rate Limiting.
- Input Validation.
- Output Sanitization.
- CSRF Protection عند انطباقها.
- حماية من SQL Injection.
- حماية من XSS.
- حماية من IDOR.
- التحقق من Webhooks.
- منع Replay Attacks عند الحاجة.

5. QR Security

- استخدام Tokens عشوائية عالية القوة.
- تخزين Hash للرموز عند الحاجة.
- منع تخمين الروابط.
- إمكانية إلغاء QR.
- منع تكرار عمليات الانضمام.

6. Loyalty Transaction Security

- منع التلاعب بالنقاط.
- منع الاستبدال المزدوج.
- استخدام Atomic Database Transactions.
- Idempotency.
- تسجيل الموظف المسؤول عن كل عملية.
- إنشاء سجل عكسي عند إلغاء المعاملة بدل حذفها.

7. Wallet Security

- حماية authenticationToken.
- حماية مفاتيح توقيع Apple.
- حماية Google Service Account.
- عدم إظهار الأسرار في الواجهة.
- منع تزوير طلبات تحديث البطاقات.
